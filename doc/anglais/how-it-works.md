# How it works

## The idea that makes it possible

Following a voice through a text seems to require excellent speech
recognition. It does not, and that is what makes this tool feasible.

Dictation software must answer: "what did the person say?" — an open question
whose answer could be any word in the language.

A teleprompter **already knows the text**. Its question is: "where has the
speaker got to?" — and the answer is necessarily one of the few dozen positions
around where they were a second ago.

The direct consequence: **a mediocre speech engine is good enough.** The
transcript is not compared against the whole language, but against a window of
thirty words known in advance.

## The method

At any moment the tool keeps the last ten words heard. It compares them with
the stretch of text around the current position, looking for the best possible
match — a local alignment algorithm borrowed from biological sequence
comparison.

Two refinements make the difference:

**Comparison is phonetic as much as written.** A speech engine does not fail at
random: it confuses words that *sound* alike. In French, "ces", "ses" and
"c'est" produce the same phonetic code and are therefore treated as equivalent,
where a letter-by-letter comparison would fail.

**Reading errors are expected, not punished.** Skipping a word of the text costs
little; hearing a word absent from the text costs little too. These are exactly
the two errors of a real reading — swallowed syllables, hesitations, "um",
improvisation — and the algorithm absorbs them instead of losing track.

## The numbers

Measured on a 147-word speech, ten runs per scenario. *Drift* is the gap, in
words, between the displayed position and the reader's real position.

| Situation | Median drift | Within 3 words | Reaches the end |
|---|---|---|---|
| Perfect reading | 0 | 100 % | 100 % |
| 25 % of words misrecognised | 0 | 100 % | 100 % |
| 40 % of words misrecognised | 0 | 100 % | 100 % |
| 35 % of words lost by the mic | 0 | 99.8 % | 90 % |
| Hesitations, stray words | 0 | 100 % | 100 % |
| **Quiet room, close mic** | 0 | 99.9 % | 100 % |
| Combined degraded conditions | 0 | 99.4 % | 100 % |
| 12-word improvised aside | 0 | 100 % | 100 % |
| An entire paragraph skipped | 0 | 93.0 % | 100 % |

Reproducible with `npm run bench`.

## The weak spot, and its fix

The first version held 99 % on ordinary text but dropped to **85.9 % on a text
with anaphora** — "I tell you…" repeated three times. And it dropped there
*even with a perfect transcript*: so it was not noise, but ambiguity in the
text itself. The engine was locking onto the wrong occurrence.

Anaphora, of course, is precisely a rhetorical device.

Tuning disproved the initial intuition: penalising distant jumps does almost
nothing. The real lever is the **backward window** — how many words the engine
allows itself to go back — which is the recovery mechanism. Widened from 12 to
20 words, it takes this case from **85.9 % to 98.8 %**.

Reproducible with `node test/stress.js`.

## Where the two modes come from

The same tuning revealed a trade-off, and that trade-off is what grounds
**Reading** and **Speech**:

- a **long** buffer of heard words brings context and resolves the ambiguity of
  repetitive texts, but reacts more slowly when the speaker jumps elsewhere;
- a **short** buffer does exactly the opposite.

You cannot have both. Hence two profiles: **Reading** favours precision,
**Speech** favours responsiveness.

## The speech engines

The app depends on no particular engine: they are interchangeable behind a
single interface.

| Engine | Where it runs | Cost | Offline | Desktop |
|---|---|---|---|---|
| **Vosk** | on your device | free | yes | yes |
| **Web Speech** | Google's servers | free | no | **no** |
| **Simulation** | nowhere — it replays the text | free | yes | yes |

About Vosk, verified by measurement: the engine is 3 MB, starts on 16 MB of
memory and can grow to 2 GB; it compiles in 9 milliseconds and instantiates in
1; it uses no shared memory and **contacts no server** at runtime.

The compute cost of tracking is 130 microseconds per word on a 2,000-word text
— about three thousand times faster than real time. Tracking is not a
performance problem.

## Code layout

```
src/align/    French normalisation, phonetics, similarity, alignment
src/script/   annotation parsing and teleprompter rendering
src/stt/      speech engine adapters and a reading simulator
src/store/    the speech library
src/ui/       design tokens, themes, fonts, assembly
electron/     desktop wrapper
android/      Android project generated by Capacitor
test/         tests, benchmark, breaking-point test
tools/        Vosk verification harness for a phone
```

The core is plain JavaScript with no runtime dependency and no build step: the
browser and Node run it as-is. That is what lets both wrappers display the same
code without rewriting it.

## Contributing

```bash
npm test              # 39 tests
npm run bench         # alignment quality, scenario by scenario
node test/stress.js   # breaking-point search
```

One rule: the alignment engine is not modified without running the benchmark. A
passing test proves nothing if the threshold is lenient — `bench` and `stress`
are what tell you by how much.
